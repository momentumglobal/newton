Platform Overview

Newton is a recruitment reporting and workforce management platform built for Momentum Global. It is a static web application hosted on GitHub Pages, with Microsoft Azure AD for authentication and SharePoint as its data backend.

There is no server-side logic. All data access is performed client-side via the Microsoft Graph API using an authenticated MSAL token. Role-based access control is enforced at the UI layer using role data fetched from SharePoint on sign-in.

Modules

Newton is organised into five functional modules, each a self-contained HTML page with its own script stack. A sixth admin interface exists outside the module system.

Reporting
reporting.html
Core recruitment reporting. Projects, Roles, Weekly Activity, Placements, Rejected Offers, Project & Company Dashboards, Report Builder, and Hiring Plan (Gantt-style hiring roadmap for CoE projects).
Market Analytics
market-reporting.html
Market intelligence and placement analytics. Create, edit and publish structured market reports linked to roles. Analyse historical placement data by location and functional area to predict time to hire and funnel drop-off.
People
people.html
Workforce management. Employee tracker, deployment timeline (Gantt), assignment tracking, Supplier invoice management. Includes Engagement tab — quarterly pulse survey builder, results dashboard, and trends view (Admin/Leadership only).
Sales
sales.html
Sales pipeline & commercial tooling. Revenue Tracking (estimated + forecast monthly revenue chart, default landing) and Sales Forecast pipeline management (Admin/Leadership), plus LCI Cost Models — Location & Cost Intelligence recruitment ramp & cost models with compare, branded PDF report export, Hiring Plan linkage and salary benchmarks (Admin/Leadership + Delivery Managers, scoped to their models). Also LCI Lead Magnet — a lightweight location cost comparator that produces a one-page Country Comparison PDF from a shared salary library (Admin/Leadership).
MG Command Centre
command-centre.html
Executive ops dashboard. Four live RAG tiles — Revenue, Project Health, People, and Utilisation — each with an expandable detail panel. The Revenue tile expands to the full Revenue Tracking chart. Available to Admin and Leadership only.
Mobile App (PWA)
mobile.html
Installable phone app (Progressive Web App) over the same codebase. Home launcher + module switcher; mobile views for Reporting (full), People (dashboard + scorecards), Sales (forecast) and Market Analytics (placement analytics). See the Mobile App section.

MG Command Centre — RAG logic

Each CC tile uses a dedicated RAG calculation. Project Health, People and Utilisation are driven by shared functions in analytics.js; Revenue is driven by the shared revenue helpers in utils.js.

TileSignalGreenAmberRed
Revenue3-month avg of estimated + forecast monthly revenue (current month + next 2). Estimated from Assignments (computeMonthlyRevenueForYear()); forecast from SalesForecasts (computeMonthlyForecastRevenueForYear())≥£225k≥£200k<£200k
Project Health% of live roles flagged (days-open vs stage timeline + submission conversion <50%)<25%≤50%>50%
PeopleWeighted flagged-role score across TPs (green=0, amber=1, red=2) ÷ TP count<0.5≤1.0>1.0
Utilisation13-week forecast % (known assignments this month via computeMonthlyRows() + SalesForecasts headcount / total active headcount)≥85%≥75%<75%
RAG thresholds are centralised in config.js: Utilisation in CONFIG.UTILISATION_THRESHOLDS (green: 0.85, amber: 0.75) and Revenue in CONFIG.REVENUE_THRESHOLDS (green: 225000, amber: 200000 — monthly £). Never hardcode these values in page scripts.

Health tile trend arrow

The Health tile shows a small trend arrow next to its title once 3+ distinct weeks of Snapshots history exist, comparing the two most recent weeks' company-wide FlaggedCount ÷ OpenRoles ratio across active projects. Green/down = improving, red/up = worsening, grey/flat = unchanged. Below 3 weeks it renders nothing. A ? tooltip beside the title explains the mechanism regardless of whether the arrow itself is showing. Logic lives in computeHealthTrend() / _ccTrendArrowHTML() in cc-pages.js — deliberately not promoted to analytics.js, since nothing else consumes it. Revenue, People and Utilisation tiles do not get a trend arrow (no Snapshots-backed data for Revenue; Utilisation was descoped; People's RAG needs a per-TP breakdown Snapshots doesn't track).

Mobile App

Newton is installable on phones as a Progressive Web App (PWA). It is the same web application served from mobile.html, not a separate native build — so it shares one codebase, one data model and one auth flow with the desktop site. Earlier prototyping used a Flutter WebView wrapper; this was retired in favour of the PWA, which runs in the device browser engine and avoids embedded-WebView authentication issues.

Installing

On the phone, open momentumglobal.github.io/newton/mobile.html in Chrome (Android) or Safari (iOS), then choose "Add to Home screen" / "Install app". A Newton icon is added to the home screen and launches standalone (no browser address bar). Sign-in uses the same Microsoft account as the desktop site.

How it works

PieceFilePurpose
Manifestmanifest.webmanifestDeclares the app name, icons (navy Momentum mark, 192/512px), standalone display and #090546 theme. Makes the site installable.
Service workersw.jsNetwork-first and caches no app code, so there is never stale JS after a commit. Ignores cross-origin and non-GET requests, so Microsoft login and SharePoint writes are never intercepted.
Mobile entrymobile.htmlRegisters the service worker, sets a newton_mobile localStorage flag (so desktop pages redirect back to mobile after the login round-trip), and loads the mobile script stack.

Mobile shell & navigation

After login the app lands on a Home launcher — a role-aware grid of modules. A top-bar module switcher dropdown moves between modules; each module has its own bottom-nav tabs. Both are driven by CONFIG.OS_MODULES (single source of truth) filtered through MOBILE_MODULES — a module appears only if it has a built mobile view and the user's role allows it. Command Centre is intentionally excluded from mobile.

Access

Mobile access is restricted to Talent Partners, Delivery Managers and Admins. Per-module visibility follows the same CONFIG.OS_MODULES roles as desktop — e.g. a Talent Partner does not see Sales but does see Market Analytics; Scorecards are role-scoped (TP sees own, DM sees their projects' TPs, Admin sees all).

Adding a module to mobile

Mirror the desktop convention: create a mobile-<module>.js renderer that reuses the existing data/calculation functions, add the module key to MOBILE_MODULES, add a MOBILE_NAV entry and default view, route its views in mobileRenderView(), and load the script in mobile.html. No Flutter rebuild is ever required — the installed PWA picks up changes on next load.

Script Load Order

All HTML files must load scripts in this order. Deviating causes "X is not defined" errors because later scripts depend on globals defined by earlier ones.

Critical: utils.js must always load before api.js. api.js calls functions defined in utils.js (ghost mode helpers, button loading state). This applies to every HTML file including admin.html and index.html.

Read Flow

Sequential write bursts (model copy, plan generation, bulk plan delete) rely on this — never add per-call retry loops in page scripts.

Coding Conventions

Established during the v1 refactor audit (June 2026). Apply to all future Newton build work.

Single source of truth

Any value referenced in more than one place lives in exactly one file. CONFIG.OS_MODULES is the canonical example — it defines the module switcher for all nav files. CONFIG.UTILISATION_THRESHOLDS defines utilisation RAG thresholds for both the People Dashboard and the Command Centre; CONFIG.REVENUE_THRESHOLDS defines revenue RAG bands for the Sales Revenue Tracking chart, the CC Revenue tile and the homepage Revenue pill. Adding a new module means editing config.js only.

File responsibilities — hard rules

  • Never put UI helpers in api.js. Never put API calls in utils.js.
  • api.js owns all Graph API calls. If it touches the network, it lives here.
  • utils.js owns pure functions with no network I/O — formatting, calculations, button state, ghost helpers.
  • nav-core.js owns the sidebar renderer. Do not write sidebar HTML in module nav files.
  • *-app.js files handle init only — MSAL redirect, role resolution, first navigation.
  • analytics.js owns shared analytics logic — isRoleFlagged(), ACTIVE_STAGES, STAGE_ORDER, computeVelocityScore(). Never duplicate these in page scripts.

CSS over inline styles

  • Conditional styling uses CSS classes, not inline style="" attributes.
  • Scope classes to their context: .dash-panel .row-age-critical td prevents bleed into unrelated tables.
  • Colour values live in style.css only. JavaScript never hardcodes hex colours.
  • Design tokens (Aug 2026): style.css opens with a :root block — --c-* colours, --sp-* spacing, --r-* radius, --fs-*/--fw-* type, --sh-* shadows, --dur-* durations. New CSS uses var() tokens; never define or shadow --org-print-scale (set at runtime by org-chart.js). Literal-vs-token mapping decisions live in newton-pipeline/specs/N-067-mapping.md.
  • Dark mode (Aug 2026): a second tier, --c-dark-* palette tokens plus a [data-theme="dark"] block, redefines the themeable subset of the N-101 semantic layer — component rules never change. The full light→dark mapping and the permanently-dark-chrome exclusion list live in newton-pipeline/specs/N-102-mapping.md. js/theme-init.js is a deliberate exception to normal script placement: it must load first in <head>, unmarked (no defer/async), on every page linking css/style.css, so the theme is set before first paint. mobile.html is excluded — it does not use css/style.css.

Output escaping

  • Data interpolated into HTML uses the utils.js helpers by context: text → escHtml (multi-line: escHtmlLines), double-quoted attribute → escAttr, JS string inside an attribute handler → escJsAttr.
  • Escape inside the .map() that builds an option/row string, never again where the composed variable is interpolated — composed markup stays raw.
  • Never escape inside comparison expressions (selected/checked ternaries compare raw values).

Project types and split-fee revenue (N-116)

  • Two enums, deliberately not one. CONFIG.PROJECT_TYPES drives the Projects list and the Sales Forecast (Embedded, CoE, Exec Search, MG AI); CONFIG.ASSIGNMENT_PROJECT_TYPES drives Assignments and adds Transformation, LCI, Internal. Projects.ProjectType gates the Hiring Plan page, the LCI link picker and the Report Builder CoE panel, so its list stays narrow. Never redeclare either in a page file.
  • Project-type colours are --c-ptype-* tokens in style.css, surfaced to JS as var() strings via CONFIG.PROJECT_TYPE_COLOUR_VARS. No hex in JS.
  • Split-fee lines (CONFIG.SPLIT_FEE_PROJECT_TYPES — Exec Search, MG AI) recognise two un-pro-rated lump sums: the retainer in the assignment's start month, the placement fee in the month after its end month. The placement month sits outside the assignment window and may fall in the next calendar year — any loop over "months this assignment overlaps" needs one extra month.
  • A row is either monthly-rate or split-fee, never both. The unused side is written null on save so a type change leaves nothing stale behind to double-count.
  • Month arithmetic on the split-fee path uses monthKeyFromISO() / addMonthsToKey() in utils.js, never new Date().getMonth(). These slice YYYY-MM straight from the ISO string. SharePoint returns UTC; parsed in BST a month-boundary date can shift a day, and for a lump sum that moves the entire fee into the wrong month — at a year end, the wrong year. This is the same class of bug as the WeekEndingDate gotcha.

Dynamic over hardcoded

Time-sensitive values are derived at runtime. Example: PLACEMENT_YEARS uses Array.from({length:4}, (_, i) => new Date().getFullYear() - i) — it never needs updating. Utilisation thresholds use CONFIG.UTILISATION_THRESHOLDS — never hardcode 0.85 or 0.75 in page scripts.

No duplicate logic

  • If the same function exists in more than one file, extract it to a shared file.
  • Never re-sort data already sorted by the API layer.
  • Never re-fetch data already cached in a window._ variable.
  • isRoleFlagged() is defined once in analytics.js and used by cc-pages.js, analytics-pages.js, and index.html — do not redefine it locally.

Nav optimisation

Use updateNavActiveLink(page) on navigation — not a full renderNav() rebuild. The full render runs once on init only. This prevents sidebar flicker and unnecessary DOM work on every page click.

Testing (Aug 2026)

Fixture assertions against the pure calc/helper layer live in tests/. Open tests/index.html in a browser for a visual pass/fail table, or run node tests/run.js (no dependencies) for the same result on the command line — the latter is also what .github/workflows/static.yml's test job runs before every deploy. tests/fixtures.js and tests/assertions.js are shared by both entry points unmodified, so they never drift apart.

Timezone discipline (Aug 2026)

Two standing rules, both handled by named helpers in utils.js rather than convention/comments: WeeklyActivity.WeekEndingDate is a Sunday, not Friday — bucket on that boundary via getWeekEnding(date). SharePoint returns dates as UTC datetimes, so toISOString() or raw string-slicing on a Date object shifts the 1st of a month into the prior month under BST — for the write side (a Date object going out) use spDateOut(date); for the read side (a SharePoint string coming in) use spDateIn(str). isoDate() (date-input-string → write string) and utcDateOnly() (SharePoint string → safe Date for arithmetic) remain in use for their existing call sites and are not deprecated by N-087 — spDateOut/spDateIn cover the two shapes those didn't: a Date object going out, and a safe day-string (no Date construction) coming in.

N-129 (13 Aug 2026): getWeekEnding() had exactly this bug — it computed the right Sunday in local terms but returned it via toISOString(), which rolled it back a day during BST. Fixed to read local getters directly instead of round-tripping through UTC. Affected only the bare getWeekEnding() call in admin.js's writeSnapshotsNow(); the forms.js/mobile-pages.js call sites pass a date-only string, which was never affected.

N-096 (Aug 2026): the date/week layer now has real test coverage in tests/ — getWeekEnding, getISOWeek, isoDate, spDateIn/spDateOut, and a dedicated coeWeekIndex regression that locks the N-077/N-081 GMT/BST Gantt class shut. That last assertion only reproduces under a DST-observing timezone, so tests/run.js forces TZ=Europe/London; tests/index.html detects when a browser's own timezone can't show the same skew and renders SKIP rather than a meaningless PASS.

Adding a New Module

Follow this checklist in order. Steps 1 and 6 are the most commonly forgotten.

  • config.js — Add entry to CONFIG.OS_MODULES with key, name, icon, href, live, and roles array. This is the only place the module switcher is defined.
  • [module]-router.js — Create page registry. Define PAGES object, canAccess(), and getAccessiblePages().
  • [module]-nav.js — Create nav wrapper. Call renderModuleNav() with subtitle, currentModuleKey, toggleFn, pages, currentPage, role, navigateFn, userGuideHref. Add toggle function and navigateTo[Module]().
  • [module]-app.js — Handle MSAL redirect, call getEffectiveRole(), redirect if role not permitted, call ensureUserRegistered(), render nav, navigate to first page. Set document.getElementById('app-shell').style.display = 'flex' after auth.
  • [module]-pages.js and [module]-forms.js — Create page renderers and form logic as needed.
  • [module].html — Follow script load order exactly: config → auth → utils → api → [module]-router → nav-core → [module]-nav → [module]-forms → [module]-pages → [module]-app. Load analytics.js before app.js if the module uses isRoleFlagged() or other shared analytics functions.
  • admin.html sidebar — Add <a class="admin-nav-link"> entry if the module needs admin panel access.
  • os-admin.js — Update role/access lists if the new module has different access requirements.
The Report Builder's REPORT_PANELS registry in dashboard-project-panels.js is the pattern for adding new report panel types — each panel is a function that takes data and a period and returns HTML.

Backlog & Future Work

Known improvement opportunities and architectural considerations for future development.

Architectural considerations (future builds)

AreaConsideration
Data volumegetItems() fetches all records and filters client-side. As data grows (especially WeeklyActivity), consider adding server-side OData filters to reduce payload size.
Multi-project usersDM and TP users can be assigned to multiple projects. The scoping model handles this but the UX could be more prominent for users with many assignments.
Real-time updatesThe 30s API cache means two users editing simultaneously may see stale data briefly. For higher-traffic scenarios, consider a shorter TTL or manual refresh triggers.
Report Builder exportPDF export uses window.print(). Server-side generation would give more reliable formatting across browsers.
Offline / error statesGraph API failures show a basic error message. A structured error boundary with retry logic would improve resilience on poor connections.
Module expansionThe module pattern (router / nav / app / pages / forms) is repeatable. New modules can be added without touching shared platform code — only config.js needs updating for the switcher.
Command Centre alertsFuture: push notifications or email digest when a CC tile flips to Red.
CCStatus freshnessCCStatus is only updated when an Admin or Leadership user loads the CC or triggers a homepage refresh. Consider a scheduled write from the CC page to keep state fresh.
