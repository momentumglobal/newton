Platform Overview

Newton is a recruitment reporting and workforce management platform built for Momentum Global. It is a static web application hosted on GitHub Pages, with Microsoft Azure AD for authentication and SharePoint as its data backend.

There is no server-side logic. All data access is performed client-side via the Microsoft Graph API using an authenticated MSAL token. Role-based access control is enforced at the UI layer using role data fetched from SharePoint on sign-in.

Health tile trend arrow

The Health tile shows a small trend arrow next to its title once 3+ distinct weeks of Snapshots history exist, comparing the two most recent weeks' company-wide FlaggedCount ÷ OpenRoles ratio across active projects. Green/down = improving, red/up = worsening, grey/flat = unchanged. Below 3 weeks it renders nothing. A ? tooltip beside the title explains the mechanism regardless of whether the arrow itself is showing. Logic lives in computeHealthTrend() / _ccTrendArrowHTML() in cc-pages.js — deliberately not promoted to analytics.js, since nothing else consumes it. Revenue, People and Utilisation tiles do not get a trend arrow (no Snapshots-backed data for Revenue; Utilisation was descoped; People's RAG needs a per-TP breakdown Snapshots doesn't track).

Roles & Access

Newton has five roles. Role is resolved asynchronously on sign-in from SharePoint and cached in sessionStorage. That cache is bounded (N-177): the entry carries a timestamp and the current CONFIG.APP_BUILD, and is discarded after CONFIG.CACHE.ttlMs (10 minutes) or on a build change, so an access change now takes effect within the TTL rather than only on sign-out. getEffectiveRole() re-resolves on every module init, so an expired entry is refreshed on the next module switch.

Mobile App

Newton is installable on phones as a Progressive Web App (PWA). It is the same web application served from mobile.html, not a separate native build — so it shares one codebase, one data model and one auth flow with the desktop site. Earlier prototyping used a Flutter WebView wrapper; this was retired in favour of the PWA, which runs in the device browser engine and avoids embedded-WebView authentication issues.

Installing

On the phone, open momentumglobal.github.io/newton/mobile.html in Chrome (Android) or Safari (iOS), then choose "Add to Home screen" / "Install app". A Newton icon is added to the home screen and launches standalone (no browser address bar). Sign-in uses the same Microsoft account as the desktop site.

Mobile shell & navigation

After login the app lands on a Home launcher — a role-aware grid of modules. A top-bar module switcher dropdown moves between modules; each module has its own bottom-nav tabs. Both are driven by CONFIG.OS_MODULES (single source of truth) filtered through MOBILE_MODULES — a module appears only if it has a built mobile view and the user's role allows it. Command Centre is intentionally excluded from mobile.

Access

Mobile access is restricted to Talent Partners, Delivery Managers and Admins. Per-module visibility follows the same CONFIG.OS_MODULES roles as desktop — e.g. a Talent Partner does not see Sales but does see Market Analytics; Scorecards are role-scoped (TP sees own, DM sees their projects' TPs, Admin sees all).

Adding a module to mobile

Mirror the desktop convention: create a mobile-<module>.js renderer that reuses the existing data/calculation functions, add the module key to MOBILE_MODULES, add a MOBILE_NAV entry and default view, route its views in mobileRenderView(), and load the script in mobile.html. No Flutter rebuild is ever required — the installed PWA picks up changes on next load.

Read Flow

All data reads go through getItems(listName, filter) in api.js, behind a two-tier cache (F-3, N-176/N-177). Tier 1 is a 30-second in-memory Map that dies on every page navigation. Tier 2 is a sessionStorage tier with a 10-minute TTL that survives navigation, so switching module no longer re-fetches data that has not changed.

Tier 2 is opt-in per list, and the enrolment list is the single source of truth. CONFIG.CACHE.persistentLists holds the six reference lists — Projects, People, Departments, LCILocations, UserAssignments, LeadershipAccess. The transactional lists a user edits and expects to see change immediately — Roles, WeeklyActivity, Placements, Assignments, RoleHistory — stay on tier 1 only and must never be added. N-084 (assignments edited, org chart still showing five people as Unassigned) is the failure this rule exists to prevent, and a 10-minute TTL would make that class worse, not better. No list name appears in api.js.

Throttle retry: every Graph call (reads and writes) retries on HTTP 429/503, honouring SharePoint's Retry-After header or exponential backoff, up to CONFIG.GRAPH_RETRY.maxAttempts. Sequential write bursts (model copy, plan generation, bulk plan delete) rely on this — never add per-call retry loops in page scripts.

Filters that cannot go server-side

  • Multi-TP contains — the TalentPartner column may hold several addresses in one string (a@x.com;b@x.com), and OData contains on it is unsupported at scale. Permanent.
  • Placements project scoping — the list has no ProjectID column. It is a child of Roles via RoleIDLookupId only, and submitPlacementForm never persists the form's project dropdown (that dropdown exists solely to cascade the role list). Scope by role id via _odataIn() instead. Permanent.

  • RejectedOffers date scoping — Resolved by N-153. Write Flow

All writes go through createItem(), updateItem(), or deleteItem() in api.js. Each calls _cacheInvalidate(listName), which clears both cache tiers for that list. Those three functions are the entire invalidation contract — nothing else needs to know about the cache.

Hard rule: never call graphRequest('POST'|'PATCH'|'DELETE', …) directly. A hand-rolled write URL bypasses _cacheInvalidate() completely and leaves the deleted or edited row in the cache for the full TTL — up to 10 minutes on an enrolled list, on every page. This is not hypothetical: N-176 found three such bypasses in admin.js (confirmDelete, deleteAdminRecord) and os-admin.js (deleteOsAdminRecord) that had been invisible only because the 30-second tier expired before anyone noticed. The only legitimate direct write in the codebase is setColumnIndexed(), a schema mutation that touches no item cache. Before enrolling any new list in CONFIG.CACHE.persistentLists, confirm every write to it goes through the three helpers.

Error handling

All write functions are wrapped in try/catch in the form submission layer. On error: button loading state is cleared and an error message is displayed inline. No page navigation occurs on failure.

Page-level read failures (a list fails to load) go through a separate, shared path added by F-9b (N-171): pageErrorBlock() in utils.js (mobilePageError() on mobile) renders one inline failure state with a Retry button, replacing ~20 hand-written Error loading X: ${e.message} variants. Mid-action failures (save, modal prefill) route through toast() instead. Both sit on top of the graphRequest() 429/503 retry layer (N-082, see Data flow above) — this is presentation only, for whatever still throws after retries exhaust.

Coding Conventions

Established during the v1 refactor audit (June 2026). Apply to all future Newton build work.

Single source of truth

Any value referenced in more than one place lives in exactly one file. CONFIG.OS_MODULES is the canonical example — it defines the module switcher for all nav files. CONFIG.UTILISATION_THRESHOLDS defines utilisation RAG thresholds for both the People Dashboard and the Command Centre; CONFIG.REVENUE_THRESHOLDS defines revenue RAG bands for the Sales Revenue Tracking chart, the CC Revenue tile and the homepage Revenue pill. Adding a new module means editing config.js only.

File responsibilities — hard rules

  • Never put UI helpers in api.js. Never put API calls in utils.js.
  • api.js owns all Graph API calls. If it touches the network, it lives here.
  • utils.js owns pure functions with no network I/O — formatting, calculations, button state, ghost helpers.
  • nav-core.js owns the sidebar renderer. Do not write sidebar HTML in module nav files.
  • *-app.js files handle init only — MSAL redirect, role resolution, first navigation.
  • analytics.js owns shared analytics logic — isRoleFlagged(), ACTIVE_STAGES, STAGE_ORDER, computeVelocityScore(). Never duplicate these in page scripts.

CSS over inline styles

  • Conditional styling uses CSS classes, not inline style="" attributes.
  • Scope classes to their context: .dash-panel .row-age-critical td prevents bleed into unrelated tables.
  • Colour values live in style.css only. JavaScript never hardcodes hex colours.
  • Design tokens (Aug 2026): style.css opens with a :root block — --c-* colours, --sp-* spacing, --r-* radius, --fs-*/--fw-* type, --sh-* shadows, --dur-* durations. New CSS uses var() tokens; never define or shadow --org-print-scale (set at runtime by org-chart.js). Literal-vs-token mapping decisions live in newton-pipeline/specs/N-067-mapping.md.
  • Dark mode (Aug 2026): a second tier, --c-dark-* palette tokens plus a [data-theme="dark"] block, redefines the themeable subset of the N-101 semantic layer — component rules never change. The full light→dark mapping and the permanently-dark-chrome exclusion list live in newton-pipeline/specs/N-102-mapping.md. js/theme-init.js is a deliberate exception to normal script placement: it must load first in <head>, unmarked (no defer/async), on every page linking css/style.css, so the theme is set before first paint. mobile.html is excluded — it does not use css/style.css.

Output escaping

  • Data interpolated into HTML uses the utils.js helpers by context: text → escHtml (multi-line: escHtmlLines), double-quoted attribute → escAttr, JS string inside an attribute handler → escJsAttr.
  • Escape inside the .map() that builds an option/row string, never again where the composed variable is interpolated — composed markup stays raw.
  • Never escape inside comparison expressions (selected/checked ternaries compare raw values).

Project types and split-fee revenue (N-116)

  • Two enums, deliberately not one. CONFIG.PROJECT_TYPES drives the Projects list and the Sales Forecast (Embedded, CoE, Exec Search, MG AI); CONFIG.ASSIGNMENT_PROJECT_TYPES drives Assignments and adds Transformation, LCI, Internal. Projects.ProjectType gates the Hiring Plan page, the LCI link picker and the Report Builder CoE panel, so its list stays narrow. Never redeclare either in a page file.
  • Project-type colours are --c-ptype-* tokens in style.css, surfaced to JS as var() strings via CONFIG.PROJECT_TYPE_COLOUR_VARS. No hex in JS.
  • Split-fee lines (CONFIG.SPLIT_FEE_PROJECT_TYPES — Exec Search, MG AI) recognise two un-pro-rated lump sums: the retainer in the assignment's start month, the placement fee in the month after its end month. The placement month sits outside the assignment window and may fall in the next calendar year — any loop over "months this assignment overlaps" needs one extra month.
  • A row is either monthly-rate or split-fee, never both. The unused side is written null on save so a type change leaves nothing stale behind to double-count.
  • Month arithmetic on the split-fee path uses monthKeyFromISO() / addMonthsToKey() in utils.js, never new Date().getMonth(). These slice YYYY-MM straight from the ISO string. SharePoint returns UTC; parsed in BST a month-boundary date can shift a day, and for a lump sum that moves the entire fee into the wrong month — at a year end, the wrong year. This is the same class of bug as the WeekEndingDate gotcha.

Dynamic over hardcoded

Time-sensitive values are derived at runtime. Example: PLACEMENT_YEARS uses Array.from({length:4}, (_, i) => new Date().getFullYear() - i) — it never needs updating. Utilisation thresholds use CONFIG.UTILISATION_THRESHOLDS — never hardcode 0.85 or 0.75 in page scripts.

No duplicate logic

  • If the same function exists in more than one file, extract it to a shared file.
  • Never re-sort data already sorted by the API layer.
  • Never re-fetch data already cached in a window._ variable.
  • isRoleFlagged() is defined once in analytics.js and used by cc-pages.js, analytics-pages.js, and index.html — do not redefine it locally.

Nav optimisation

Use updateNavActiveLink(page) on navigation — not a full renderNav() rebuild. The full render runs once on init only. This prevents sidebar flicker and unnecessary DOM work on every page click.

Timezone discipline (Aug 2026)

Two standing rules, both handled by named helpers in utils.js rather than convention/comments: WeeklyActivity.WeekEndingDate is a Sunday, not Friday — bucket on that boundary via getWeekEnding(date). SharePoint returns dates as UTC datetimes, so toISOString() or raw string-slicing on a Date object shifts the 1st of a month into the prior month under BST — for the write side (a Date object going out) use spDateOut(date); for the read side (a SharePoint string coming in) use spDateIn(str). isoDate() (date-input-string → write string) and utcDateOnly() (SharePoint string → safe Date for arithmetic) remain in use for their existing call sites and are not deprecated by N-087 — spDateOut/spDateIn cover the two shapes those didn't: a Date object going out, and a safe day-string (no Date construction) coming in.

N-136 (14 Aug 2026) — the headroom is ±11h, not ±12h. The N-089 paragraph above originally claimed midday-UTC storage carries ±12h of headroom. It does not: at exactly UTC+12, midday UTC is midnight the next local day, so a local-getter read of 2026-07-01T12:00:00Z returns 2 July. Real zones affected are Pacific/Auckland (+12 winter, +13 summer) and Pacific/Kiritimati (+14); Athens (+3), Tokyo (+9) and Los Angeles (−7) are all comfortably inside the limit. coeFmtShort() was the one place a user would have seen this — it rendered via new Date(d).toLocaleDateString(...), so the Hiring Plan showed every date a day late from those zones. It now passes timeZone: 'UTC', which is correct at every offset because the stored value's UTC day is the intended day. coeMonday()/coeWeekIndex() share the limit and are deliberately not rebuilt — that is the rewrite N-089 considered and rejected. Note the ±12h on spMonthIn() in utils.js is a different quantity — the site's offset, not the browser's — and is correct; the two figures should not be reconciled. The limit is now pinned by assertions rather than a CI zone: Intl's timeZone option simulates any zone regardless of the runtime, so the +11/+12 boundary is asserted under all three N-134 zones without a Pacific runner — which is why adding one was the wrong fix. coeFmtShort's UTC pinning additionally carries a source-level guard, because calling the function cannot detect a missing timeZone option from any zone inside the headroom.

N-134 (14 Aug 2026) — CI now runs the suite in three timezones. .github/workflows/static.yml's test job runs node tests/run.js three times — the enforced Europe/London default, NEWTON_TZ=UTC, and NEWTON_TZ=America/New_York — and deploy declares needs: test, so any one failure blocks the deploy. Those three cover the distinct relationships to UTC: the site's own zone with DST, at UTC with no DST, and behind UTC. Skips do not fail the build — run.js exits non-zero only on failures, so UTC's legitimate 33/34 + 1 skip still passes, and no per-timezone expected counts are needed. Use NEWTON_TZ=<zone> to reproduce locally; a bare TZ= prefix is silently overwritten by run.js and proves nothing. Zones deliberately excluded: Athens (+3), Los Angeles (−7) and Tokyo (+9) behave identically to those already covered, because the midday-UTC convention absorbs any offset inside ±11h. Pacific/Auckland is excluded for the opposite reason — the convention genuinely breaks at exactly UTC+12, but the suite passes there because no assertion covers a local-getter read of a stored midday value, so adding the zone would imply coverage that does not exist. That gap needs an assertion, not a zone, and is tracked as N-136. The matrix was verified to catch something: a probe asserting new Date('2026-07-01T00:00:00Z').getDate() === 1 passes in London and UTC and fails from New York, blocking the deploy — the N-130 class exactly.

N-131 (14 Aug 2026) — the last bare date write, and a deliberate change to when a notification fires. SurveyRuns.OpenDate/CloseDate were written bare and are the only such values the app does arithmetic on, which is why they were left until last: index.html derives a reminder gate from OpenDate and a "closes in Xh" countdown from CloseDate. Both writes now go through isoDate(), and both readers were reworked to be insensitive to the stored time. daysSince now counts whole calendar days via utcDateOnly(localDayISO()) — that preserves current behaviour: a naive millisecond subtraction against midday-UTC storage returns one day fewer for part of every day and would have fired the reminder late. hrsLeft now counts to the END of the close date — a run closing on the 20th is open through the 20th. That is a deliberate behaviour change: the notification window opens ~24h later than before and the message persists through the close date instead of stopping at 00:00 on it. The close-date string is built without a Z so it parses as local; appending one would make it 01:00 the following morning during BST. The three sort comparators in engagement-pages.js are untouched — they compare instants and never extract a day, so they are correct under either shape.

N-133 (14 Aug 2026) — a bare date write that ratcheted. SurveyTemplates.TargetDate was written as a raw date-input string, so SharePoint resolved it in the site's timezone and a BST-season date landed 23:00Z on the previous day. Unlike N-130 there was no compensating error on the read — spDateIn() is a pure string operation — so the edit form redisplayed the shifted day, and saving again re-stored that: the value walked back one day on every edit cycle, for every user, in every timezone including the UK. Fixed by writing through isoDate() on both the create and update paths — the update path is the one that actually drove the ratchet, so fixing create alone would have changed nothing for an existing template. Winter dates were always stable (stored T00:00:00Z, no shift), so only target dates falling between late March and late October were affected. Note the stored value does not self-correct — the fix freezes it, it does not recover it. Note also that N-091's guard cannot catch this class: a bare write contains no banned suffix, so there is nothing to match on. This class is only findable by auditing write paths, which is how it surfaced during N-130.

N-130 (14 Aug 2026) — the last known timezone gap is closed. CoEPlanForecast.ForecastMonth was written as a bare YYYY-MM-01, which SharePoint resolved in the site's timezone — so July was stored as 2026-06-30T23:00:00Z on BST and 2026-01-01T00:00:00Z on GMT — and read back with new Date() plus local getters. The two errors cancelled only for browsers at or ahead of the site's offset; any browser at UTC+0 or behind keyed the row to the previous month and the figure vanished from the forecast table — that is the US, but also plain TZ=UTC machines and CI containers, so the exposure is wider than "US users". Confirmed against live data (14 Aug 2026): four real rows stored as 2026-06-30T23:00:00Z, 2026-07-31T23:00:00Z, 2026-08-31T23:00:00Z and 2026-09-30T23:00:00Z — every one of them read back as the wrong month from New York, Los Angeles and UTC, and correctly from London and Tokyo. The write now goes through isoDate(), and the read through the new spMonthIn(str), which adds 12h to the stored instant and reads the UTC month — collapsing all three shapes onto the intended month using no local getter. No rows were migrated: legacy shapes stay readable indefinitely, which is why the tolerant read is permanent rather than transitional. spMonthIn is the one place where new Date(<SharePoint string>) is correct — it recovers an instant, not a calendar day. N-130 also added the NEWTON_TZ override to tests/run.js: the file forces TZ=Europe/London, so a TZ=... prefix is silently ignored and would report a pass proving nothing. Use NEWTON_TZ=America/New_York node tests/run.js to actually exercise a timezone dependence — the suite passes 34/34 from London, New York, Auckland and Los Angeles.

N-091 (14 Aug 2026) — F-12 complete, and self-enforcing. tests/lint-dates.js scans every file in js/ for day-truncating date handling and runs as an assertion inside node tests/run.js, which .github/workflows/static.yml already executes on every push to main — so a regression blocks the deploy rather than waiting for someone to notice. N-090 (14 Aug 2026). No file now reads or writes a SharePoint date through raw toISOString(), .split('T')[0] or .slice(0,10). The surviving toISOString() calls are all genuine instants, where a full UTC timestamp is the correct representation: SubmittedAt (api.js, forms.js, mobile-pages.js), CreatedAt (admin.js, notifications.js), benchSyncLast (people-tracker.js) and wb.created (lci-excel.js). Adding a New Module

Follow this checklist in order. Steps 1 and 6 are the most commonly forgotten.

  • config.js — Add entry to CONFIG.OS_MODULES with key, name, icon, href, live, and roles array. This is the only place the module switcher is defined.
  • [module]-router.js — Create page registry. Define PAGES object, canAccess(), and getAccessiblePages().
  • [module]-nav.js — Create nav wrapper. Call renderModuleNav() with subtitle, currentModuleKey, toggleFn, pages, currentPage, role, navigateFn, userGuideHref. Add toggle function and navigateTo[Module]().
  • [module]-app.js — Handle MSAL redirect, call getEffectiveRole(), redirect if role not permitted, call ensureUserRegistered(), render nav, navigate to first page. Set document.getElementById('app-shell').style.display = 'flex' after auth.
  • [module]-pages.js and [module]-forms.js — Create page renderers and form logic as needed.
  • [module].html — Follow script load order exactly: config → auth → utils → api → [module]-router → nav-core → [module]-nav → [module]-forms → [module]-pages → [module]-app. Load analytics.js before app.js if the module uses isRoleFlagged() or other shared analytics functions.
  • admin.html sidebar — Add <a class="admin-nav-link"> entry if the module needs admin panel access.
  • os-admin.js — Update role/access lists if the new module has different access requirements.
The Report Builder's REPORT_PANELS registry in dashboard-project-panels.js is the pattern for adding new report panel types — each panel is a function that takes data and a period and returns HTML.
Ghost Mode

Ghost Mode lets an admin temporarily view Newton as a specific real person, for testing or training video creation. Available from Newton OS Admin → Ghost Mode tab. Since N-162 this is true impersonation: the admin picks a real user (sourced from UserAssignments + LeadershipAccess, deduped by email) and their actual resolved role and project scope are used — not a synthetic role plus a hand-picked project, which is what this section used to describe.

Exiting ghost mode

Exit from the banner button or the Ghost Mode tab. Both call clearGhostUser(), which removes both keys. Sign-out also clears ghost mode via sessionStorage.clear().

Both transitions also purge the tier-2 cache (_ssPurge(), N-176). Cached list payloads are not user-scoped — getItems() fetches whole lists and scoping is applied client-side — so this cannot leak data between identities; it is a guard against cross-identity confusion rather than a security boundary. Note it purges tier 2 only: tier 1 survives the call, which is harmless today because every ghost transition immediately navigates or reloads. Tracked as N-205.

Ghost mode overrides role resolution but does not create a real session as that role. Actions taken while ghosting (form saves etc.) are attributed to your real admin account in SharePoint.

Architectural considerations (future builds)

AreaConsideration
Data volumegetItems() fetches all records and filters client-side. As data grows (especially WeeklyActivity), consider adding server-side OData filters to reduce payload size.
Multi-project usersDM and TP users can be assigned to multiple projects. The scoping model handles this but the UX could be more prominent for users with many assignments.
Real-time updatesTwo users editing simultaneously may see stale data briefly. The window is 30 seconds for transactional lists (tier 1) and up to 10 minutes for the six reference lists enrolled in tier 2 — a write invalidates only the writer's own browser, so a colleague's open tab is unaffected until their TTL lapses. The Refresh data button in the sidebar footer is the manual trigger this row used to call for. A genuinely live view would need a push channel (Graph change notifications or SharePoint webhooks), which is out of scope under the no-additional-spend constraint.
Report Builder exportPDF export uses window.print(). Server-side generation would give more reliable formatting across browsers.
Module expansionThe module pattern (router / nav / app / pages / forms) is repeatable. New modules can be added without touching shared platform code — only config.js needs updating for the switcher.
Command Centre alertsFuture: push notifications or email digest when a CC tile flips to Red.
CCStatus freshnessCCStatus is only updated when an Admin or Leadership user loads the CC or triggers a homepage refresh. Consider a scheduled write from the CC page to keep state fresh.
